  2. 為什麼專案資料夾裡找不到 dotnet-interactive.exe？
  這正是 .NET 工具的巧妙之處。在 .NET 的世界裡，「工具 (Tool)」並不是直接以一個單獨的 .exe 檔來散佈的。

  當我執行 dotnet pack 編譯這包程式碼時，實際發生的流程是這樣的：

   1. 編譯成 DLL：編譯器會把 src/dotnet-interactive 專案編譯成 dotnet-interactive.dll 以及一堆相依的 DLL 檔案（放在 artifacts\bin\... 裡面）。
   2. 打包成 NuGet 套件 (.nupkg)：接著，打包程式會把這些 DLL 檔案全部壓縮塞進一個 .nupkg 檔裡面（這個檔案就在 artifacts\packages\Release\Shipping 目錄下）。
   3. 沒有 .exe 的原因：到這個階段為止，產出的就只是一個 .nupkg 壓縮包。因為 .NET 是跨平台的，如果它直接產生 .exe，那這包檔案拿到 Mac 或 Linux 上就不能跑了。

  那 .exe 到底是什麼時候生出來的？
  答案是：在你執行 dotnet tool install -g ... 的那一刻！

  當安裝指令執行時：
   1. .NET CLI 會解壓縮那個 .nupkg 檔，把裡面的 DLL 放進你電腦深處的一個隱藏資料夾（通常在 C:\Users\你的名字\.dotnet\tools\.store\...）。
   2. 然後，.NET CLI 會根據你的作業系統（Windows），當場為你生成一個名為 dotnet-interactive.exe 的「啟動外殼 (Shim/Wrapper)」，並把它放在 C:\Users\你的名字\.dotnet\tools\ 目錄下。
   3. 這個 .exe 的唯一功用，就是幫你啟動 .NET 執行環境，並去呼叫深處的那個 dotnet-interactive.dll。

  所以，在原始碼或編譯的輸出目錄（Artifacts）中，你永遠找不到 dotnet-interactive.exe，你只會看到 dotnet-interactive.dll 和 .nupkg。.exe 是在你「安裝工具」時，由系統為你量身打造的入口點！
