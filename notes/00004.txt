› 1. a. raw ta-browser.v3 full snapshot -> 這是什麼?

• 先釐清一個核心概念：RuntimeFrame 是「一次狀態轉移訊息」，不是「完整畫面的檔案」。我前面把這兩個層級講在一起，才會顯得奇怪。

  1. 這些格式分別是什麼？

  ### a. raw ta-browser.v3 full snapshot

  現有正式下載檔大致是：

  ptcs-ta-research-export.v1
  └─ state
     └─ ta-browser.v3
        ├─ updateKind = "full"
        ├─ rows
        ├─ timeline
        ├─ series
        ├─ status
        ├─ query
        └─ revisions

  也就是：

  {
    "schema": "ptcs-ta-research-export.v1",
    "exportedAtUtc": "...",
    "documentRevision": 12,
    "dataRevision": 34,
    "state": {
      "wireVersion": "ta-browser.v3",
      "updateKind": "full",
      "rows": [],
      "timeline": [],
      "series": []
    }
  }

  所謂 raw ta-browser.v3 full snapshot，只是把外層 export envelope 拿掉，直接提供裡面的 state：

  {
    "wireVersion": "ta-browser.v3",
    "updateKind": "full",
    "rows": [],
    "timeline": [],
    "series": []
  }

  它不是另一套 trader-facing 格式，而是目前 browser renderer 已在使用的內部、扁平化 DTO。

  我的建議可以再收斂：

  - trader-facing 正式輸入只承認 ptcs-ta-research-export.v1
  - raw ta-browser.v3 full 僅作內部測試／程式串接能力
  - 不需要在使用說明裡要求 trader 認識 ta-browser.v3

  ### b. delta-only 是什麼？

  full 帶有建立完整畫面所需的目前狀態。

  delta 只帶「相對於上一版增加或改變的部分」，概念上像：

  我以 dataRevision=34 為基礎，
  現在新增了第 35～40 根資料，
  並把 freshness 更新為 Live。

  它不會重新攜帶完整的：

  - 所有 rows/traces
  - 全部歷史 K Bar
  - 所有 SMA／DMI／MACD 點
  - 完整 query/default view
  - 先前已存在的狀態

  所以若只有 delta、卻沒有它宣告的 baseDataRevision，無法知道：

  - 這些點應接在哪一段資料後面
  - 原本有哪些 row
  - 哪個 series 對應哪個 trace
  - navigator 的完整 loaded range
  - 缺少的資料是真的沒有，還是存在於前一版

  「拒絕 delta-only」就是：不能拿一個沒有 base state 的增量訊息，假裝它是一份完整 TA 分析檔。

  如果 notebook 裡已經存在相符的 base state，當然可以接收 delta；拒絕的是「單獨載入一份 delta 當作完整新畫面」。

  ### c. 單一 sdui-runtime.v1 RuntimeFrame 的完整邊界

  需要分成兩種完整性：

  1. Message-complete

     單一 RuntimeFrame 可以是完整、合法的一則訊息。

  2. Render-state-complete

     單一 frame 通常不足以還原完整 TA 畫面。

  現有 RuntimeFrame 的 Kind 只能是以下其中一種：

   Kind         負責內容
  ━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Document     畫面結構、rows、traces、dataRef、default view、allowed actions
  ───────────  ────────────────────────────────────────────────────────────────
   Snapshot     各 dataRef 的完整資料與 freshness
  ───────────  ────────────────────────────────────────────────────────────────
   Patch        相對於既有 snapshot 的增量變更
  ───────────  ────────────────────────────────────────────────────────────────
   Error        錯誤狀態
  ───────────  ────────────────────────────────────────────────────────────────
   Heartbeat    連線／活性資訊

  每個 frame 只有一種 Kind，而且 Kind 必須和 Payload 相符。

  一份可畫出 TA 圖的 render state，最低通常是：

  Document frame
    + Snapshot frame
    → RuntimeReducer
    → RuntimeState
    → Renderer

  更精確的邊界是：

  - Document 已定義 visible rows、traces 與其 dataRef
  - Snapshot 提供這些 dataRef 對應的資料
  - 兩者的 DocumentId／CanvasInstanceId 一致
  - revision／sequence 可以合法合併
  - 至少有能建立 shared time axis 的主要時間序列
  - 指標 warm-up 前的缺值可以合法存在，不代表整份狀態不完整

  因此，「所有指標每一點都有值」不是完整性的必要條件；但「連 row 要讀哪個 dataRef 都不知道」或「只有 dataRef、沒有資料」就不足以還原完整畫面。

  ### d. 為什麼單一 frame 只有 Document 或 Snapshot？

  這是現有型別的設計：

  type RuntimePayload =
      | Document of TaWorkspaceDocument
      | Snapshot of RuntimeSnapshot
      | Patch of RuntimePatch
      | Error of RuntimeError
      | Heartbeat of RuntimeHeartbeat

  一個 DU value 一次只能是其中一個 case。

  Document 類似圖表配置：

  第一列：K Bar + SMA13 + SMA21
  第二列：DMI7 + ADX7
  第三列：MACD 34/89/144
  共用時間軸、預設顯示最後 160 根

  它不保存 2000 根 OHLCV 與指標數值。

  Snapshot 類似資料表：

  series.es.ohlcv = [...]
  series.sma13    = [...]
  series.dmi7     = [...]
  series.macd     = [...]

  但它本身不負責告訴 renderer：

  - 哪些 series 要放同一列
  - 哪個是 candlestick、line 或 histogram
  - row 順序與高度
  - 哪些 trace 初始隱藏
  - 哪個 series 是 shared time-axis authority

  所以兩者合併才是完整 RuntimeState。

  2. 需要 backend 會不會很麻煩？

  要看是哪一種互動。

  不需要 backend 的功能：

  - navigator 拖曳
  - zoom／pan
  - vertical cross-row cursor
  - hover/current values
  - row/trace 顯示隱藏
  - browser-local Reset View

  這些只要完整 export JSON 和既有 Dynamic Renderer 即可。

  需要 backend 的功能：

  - 換商品、日期範圍、K 棒尺度
  - Add Row 並要求計算新的 SMA／DMI／MACD
  - Reset Canvas 回復後端定義的原始 document
  - 即時追加 K Bar／indicator delta
  - reconnect／resync
  - 查詢目前 JSON 沒攜帶的歷史資料

  不建議在 notebook kernel 裡啟動完整 PulseTrade.Comm.Spa.Host。它是 production executable，還會帶入：

  - Login／ACL
  - Resource Node
  - Actor fabric
  - SQL／TAResearch provider
  - production WebSocket session
  - extension loading與其他 PTCS lifecycle

  對 notebook 顯示一張 TA 圖而言太重。

  比較合理的是一個小型 InteractiveRenderHost：

  Kernel
  └─ InteractiveRenderHost（127.0.0.1）
     ├─ 保存本次 SDUI JSON
     ├─ 提供 iframe HTML
     ├─ 提供 Dynamic Renderer assets
     └─ 可選的 typed action endpoint

  靜態版本甚至只需要：

  GET /sdui/{opaque-id}
  GET /sdui/{opaque-id}/state
  GET /assets/...

  不需要 ActorSystem、登入、ACL 或 SQL。

  若需要 backend action，可以再增加一個很小的入口：

  POST /sdui/{opaque-id}/action
    SduiAction
      → backend callback
      → RuntimeFrame
      → browser reducer

  所以答案是：

  - 啟動完整 SPA Host：會很麻煩，而且責任過重。
  - 做一個「閹割版 SPA Host」：名稱與責任容易混淆。
  - 做一個用途明確的小型 InteractiveRenderHost：不算太麻煩，也是目前最適合的方向。

  第一版可以讓 InteractiveRenderHost 支援完整靜態 TA 圖與 browser-local interaction；backend 用一個 typed callback seam 保留，但目前不硬接 PTCS Host。這樣既不
  重寫 renderer，也不把整套 production SPA 塞進 notebook。

› 不同 quoteslot 都會有相同的取 1k 函數 or 方法對嗎? (類似 interface spec)


• 對，概念上就是共同的 interface spec。但目前不是設計成所有 slot 都提供一個 get1K() pull 方法，而是統一成「產生 1K step」的介面。

  目前共同型別概念如下：

  QuoteSlot<CompletedMarketBar>

  所有提供 1K 步進的 provider adapter，都要先把自己的原生格式轉成：

  CompletedMarketBar

  然後提供相同操作：

  slot.RunHistorical
      startUtc
      endUtcExclusive
      commitStep
      cancellationToken

  slot.RunLive
      commitStep
      cancellationToken

  其中每次交給 engine 的內容一致：

  QuoteStep<CompletedMarketBar>

  也就是：

  { StepIndex: int64
    EventTimeUtc: DateTimeOffset
    ReceivedTimeUtc: DateTimeOffset
    Value: CompletedMarketBar }

  所以不同來源應該是：

  MDCQ alpha.66.22 ─┐
  SQL historical    ├─ provider adapter ─> QuoteSlot<CompletedMarketBar>
  其他行情 API      ┘

  Engine 不應知道它來自 MDCQ、SQL 或其他 vendor，只吃同一種 QuoteStep<CompletedMarketBar>。

  需要特別區分兩件事：

  - QuoteSlot：逐根交付 1K，驅動 FRP NEXT／CURSOR。
  - MarketDataSlot：用 ReadTimeRange 取得整段 dataset，不驅動 NEXT。

  因此你的理解是對的：不同的 1K QuoteSlot 必須遵守相同介面；差別只能留在 adapter 與 config 內。

  目前尚未完全通用的是「任意商品、任意 scale 的 binding」。現有 alpha.66.22 factory 還是 ES-specific，但 QuoteSlot 消費端的步進介面已經相同。未來比較合理的
  trader-facing 語意會像：

  engine.BindQuote(
      "PRIMARY",
      source = "alpha66",
      instrument = "ES",
      scale = K 1
  )

  後面的 strategy 只看 PRIMARY 對應的 1K series，不碰 provider-specific API。
